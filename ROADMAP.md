# Роудмап: система ботов для накрутки просмотров в соцсетях

> Стек: Go. Без AI — только инструкции/скрипты. Старт в облаке → физический сервер.
> Цель: много ботов, много пользователей, надёжно и понятно.

---

## ⚠️ Важное предупреждение (прочитать до этапа 0)

«Боты, поднимающие просмотры» = автоматизация действий от имени множества
аккаунтов. Это почти всегда нарушение ToS соцсетей. Реальные последствия:

- массовые баны аккаунтов и IP-диапазонов;
- штрафы и блокировки со стороны платформ (софтверные патенты Meta/YouTube против скраппинга/автоматизации);
- юридические риски в ряде юрисдикций (в т.ч. РФ — ст. 272/273 УК за средства обхода блокировок и несанкционированный доступ, практика по «накрутке» есть);
- если боты работают через веб-интерфейс без API — вам придётся постоянно чинить их под изменения страниц и капчи.

**Легальные альтернативы той же бизнес-цели:** официальная реклама (VK Ads, TikTok Ads, YouTube), интеграция с биржами заданий (TaskPay, UnuSeed, Bosslike — люди, а не боты, смотрят контент), SEO/контент-автоматизация, аналитика для роста. Архитектура ниже подходит и для этого тоже.

## Этап 0 — Фундамент решения (1–2 недели)

Цель: понять, что вообще строим, и снять главные риски.

- [ ] Определить целевые платформы (одна! например VK или YouTube) и точный механизм: официальное API vs эмуляция браузера vs сторонний трафик.
- [ ] Проверить ToS платформы и наличие официального API для нужных действий.
- [ ] Решить модель: self-hosted (свой сервер) vs аренда готовых решений.
- [ ] Посчитать экономику: стоимость прокси/IP, аккаунтов, сервера на 1000 «ботов».
- [ ] **MVP-эксперимент вручную:** 5–10 аккаунтов, скрипт на 200 строк Go — посмотреть, что банится и как быстро. Это даст реальные требования к антидетекту.

**Выход:** одностраничный документ «механизм + риски + бюджет», решение «пишем / покупаем / арендуем».

## Этап 1 — MVP: один бот-воркер (2–4 недели)

Цель: один Go-процесс надёжно выполняет одну задачу многократно.

- [ ] Каркас проекта: `go mod init`, структура `cmd/ worker`, `internal/`.
- [ ] Конфигурация: `koanf` или `viper` (YAML/env).
- [ ] HTTP-клиент: стандартный `net/http` + `resty` при необходимости.
- [ ] Логгер: `slog` (стандартная библиотека, Go 1.21+).
- [ ] Планировщик задач: `robfig/cron` или простой цикл + `time.Ticker`.
- [ ] Прокси-ротация: `xp-dev/go-snippet` не нужен — свой пул + `golang.org/x/sync/semaphore` для лимита одновременных запросов.
- [ ] Retry/backoff: `avast/retry-go` или `cenkalti/backoff/v4`.
- [ ] Если нужна эмуляция браузера: `playwright-go` или `chromedp` (тяжело; держать как отдельный модуль воркера).
- [ ] Хранилище состояния: SQLite (`modernc.org/sqlite`, без CGO) — профиль аккаунта, куки, счётчики.
- [ ] Dockerfile (multi-stage, статический бинарник ~10–15 МБ).

**Критерий готовности:** воркер крутится сутки в облаке, задачи выполняются, при падении — рестартует (systemd/docker restart), логи читаемы.

## Этап 2 — Очередь и диспетчер (3–4 недели)

Цель: превратить «один скрипт» в «систему: Many workers + одна очередь».

- [ ] Брокер очереди: **NATS JetStream** (лёгкий, один бинарник, идеален для Go) или Redis + `asynq` (проще операционно, если Redis уже знаком). RabbitMQ — избыточен на этом этапе.
- [ ] Диспетчер: ставит задачи в очередь с учётом лимитов (rate limit на аккаунт/IP/платформу).
- [ ] Модель данных: `task`, `account`, `proxy`, `worker`, `result` — PostgreSQL (`pgx` + `sqlc`) или пока SQLite, если инстанс один.
- [ ] Горизонтальное масштабирование воркеров: stateless-воркеры тянут задачи из очереди; добавление мощности = `docker up --scale worker=N`.
- [ ] Идемпотентность задач (не выполнять одно и то дважды) + dead-letter очередь для «отравленных» задач.
- [ ] Heartbeat воркеров и автоудаление мёртвых.

**Критерий готовности:** 10–50 воркеров на 2–3 машинах, очередь не теряет задачи при рестарте, метрики «задач/сек, ошибок/сек».

## Этап 3 — Устойчивость и антибан (параллельно, постоянно)

Цель: система деградирует мягко, а не умирает от одной блокировки.

- [ ] Пул аккаунтов: ротация, лимиты «действий в день» на аккаунт, карантин после подозрений.
- [ ] Пул прокси: резидентные (ISP) прокси предпочтительнее датацентровых; учёт качества каждого IP, автоисключение.
- [ ] Поведенческие хаотизаторы: случайные паузы, jitter, имитация «тёплых» сессий.
- [ ] Детект капчи: либо сервис-решатель (2captcha/CapMonster — API, вписывается в Go легко), либо отказ от вектора, где капча неизбежна.
- [ ] Alerting: Telegram-бот уведомляет о волне банов/росте ошибок (ironic, но полезно).
- [ ] Feature flags по платформам: выключить вектор одним конфигом при бан-волне.

**Критерий готовности:** убийство 30% аккаунтов не останавливает систему; восстановление автоматическое.

## Этап 4 — Управление и наблюдаемость (2–3 недели)

- [ ] Панель управления: минимальная веб-админка. Варианты: Go-шаблоны + htmx, или React/Vue + REST API (`chi`/`echo`/`gin`). Не строить «красиво», строить «видно состояние».
- [ ] API (Gin или Chi) — точка входа для будущего мультипользовательского режима.
- [ ] Метрики: Prometheus + Grafana (`prometheus/client_golang`), ключевые графики: throughput, errors, бан-рейт, баланс прокси.
- [ ] Логи: JSON через `slog` → Loki или просто файловая ротация на старте.
- [ ] Аудит всех действий (кто/что/когда) — пригодится и для отчётности «пользователям».

## Этап 5 — Мультипользовательский режим (по желанию, 3–4 недели)

Если планируете продавать доступ другим:

- [ ] Авторизация: JWT/OIDC (`golang-jwt`, Keycloak если хочется «взрослости»).
- [ ] Тенанты: изоляция задач/аккаунтов по client_id (RLS в Postgres или схема на тенанта).
- [ ] Квоты и биллинг (Stripe/ЮKassa) — но см. раздел «юридика»: продажа накрутки третьим лицам резко повышает риск.
- [ ] Self-service: пользователь сам загружает аккаунты/ссылки, видит статистику.

## Этап 6 — Продакшн-инфраструктура (после MVP)

- [ ] IaC: Terraform/Pulumi с первого дня в облаке — переезд на физик потом = просто другой provider.
- [ ] CI/CD: GitHub Actions — тесты, golangci-lint, сборка docker-образа, деплой.
- [ ] Оркестрация: start с docker-compose; при >5 серверах — Kubernetes (или проще: Nomad — меньше возни, отлично для Go-воркеров).
- [ ] Backups: ежедневные дампы БД + тест восстановления.

## Про «купить готовую базу ботов»

Честная раскладка по вариантам:

| Вариант | Плюсы | Минусы |
|---|---|---|
| **Купить готовый софт/«базу ботов»** (форумы, маркетплейсы скриптов) | Быстрый старт, дёшево | Закрытый код часто, тонкий клиент = баны пачками, продавец исчезнет, обновления под changes платформы за вас никто не делает, риск бэкдоров. Для *своей* надёжной системы — плохая база |
| **Аренда сервиса накрутки** (bot-panel, SMM-панели) | Нулевая разработка | Вы не контролируете ничего, маржа уходит посреднику, ваш «роудмап» сводится к закупке |
| **Open-source фреймворки как фундамент** (см. ниже) | Бесплатно, прозрачно, можно резать под себя | Всё равно интегрировать самому |
| **Своя система на Go (этот роудмап)** | Контроль, масштабируемость, переиспользование | 2–3 месяца до устойчивого ядра |

Рекомендация: купить не «ботов», а **инфраструктурные компоненты**: резидентные прокси (самый дефицитный ресурс), возможно решатель капчи, возможно аккаунты (с огромным осторожным отношением к качеству). Код — свой, на базе open-source библиотек.

Полезные готовые кирпичики в Go:
- `go-telegram/bot`, `tbpo` — если целитесь в Telegram-экосистему легально;
- `vk-sdk` / `vasiliy-seredkin/vkapi` — официальное VK API;
- `chrome-go`/`chromedp`, `playwright-go` — браузерная автоматизация;
- `asynq` (Redis) или NATS JetStream — очередь;
- `temporal.io` — оркестрация долгих процессов (если захочется «надёжно как в(big tech)», но это overkill для этапов 1–2).

## Про хостинг

Эволюция, которая впишется в бюджет:

1. **Старт (этапы 0–2):** VPS-облако, 2–4 ядра / 8 ГБ RAM (~10–20 €/мес, Hetzner/Contabo). Go-воркеры лёгкие: сотни concurrent-задач на такой машине. Плюс отдельный маленький VPS под панель/БД или всё в одном compose.
2. **Рост (этапы 3–4):** выделенный сервер Hetzner/OVH dedicated (~40–70 €/мес, 8+ ядер, NVMe) — дешевле «физика в аренду» и уже достаточно близко к вашему плану.
3. **Свой физический сервер:** оправдан примерно от ~50–100 одновременных браузерных сессий (headless Chrome ест RAM) или от стабильного трафика в несколько сотен Гб/сутки. До этого — деньги в ветер. При выборе: больше RAM и NVMe, CPU среднего уровня достаточно; канал от 1 Gbps; размещать в data-center с дешёвым трафиком (DE/FI/NL), если платформа не гео-чувствительна.
4. **Прокси — отдельная статья бюджета:** резидентные прокси стоят 2–10× дороже сервера. Закладывайте в экономику модели с этапа 0.

## Таймлайн (суммарно ~3–4 месяца до «надёжно»)

```
Неделя 1-2   : Этап 0 — исследование, manual MVP, экономика
Неделя 3-6   : Этап 1 — воркер на Go, docker, сутки стабильной работы
Неделя 7-10  : Этап 2 — очередь, диспетчер, 10-50 воркеров
Параллельно  : Этап 3 — антибан-слой (это процесс, не этап)
Неделя 11-13 : Этап 4 — панель, метрики, алерты
(опционально): Этап 5 — мультипользовательскость
```

## Первые 3 конкретных шага

1. Написать на листке: платформа + механизм (API/браузер) + сколько просмотров/день нужно + бюджет на прокси.
2. Прогнать ручную проверку: 5 аккаунтов × 3 дня — собрать статистику банов.
3. Создать репозиторий и каркас из этапа 1 (`go mod init`, slog, cron, SQLite) — первый коммит важнее идеального плана.
